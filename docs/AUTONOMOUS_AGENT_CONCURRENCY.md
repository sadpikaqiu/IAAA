# 自主 Agent 并发测速

`scripts/benchmark_autonomous_concurrency.py` 重放已经完成的开发阶段请求，比较同一模型服务在不同请求并发下的吞吐与延迟。它不运行新的推荐评测，不读取推荐准确率来选配置，也不把测速响应放入正式结果。

## 运行条件

- 使用含 `code/`、`results/manifest.json`、`results/cases/development/`、`results/runs/development/` 的冻结实验目录。
- 两城需要已有完成的开发会话。选样只使用会话完成状态、请求类别、请求路径及第一次响应是否通过校验；不使用目标 POI、推荐名次或效果指标。
- 在服务器的 `iaaa` 环境运行，需要已有项目依赖以及 `jsonschema`（项目 `test` 可选依赖包含它）。
- 先让正式评估正常收尾。脚本会等待服务器上没有 `evaluate_autonomous.py` 进程、模型连续三次采样无运行或排队请求，才开始测速。它不会停止任何进程或模型服务。
- 输出目录必须是新目录；拒绝覆盖以前的测速记录。多个测速任务不能同时运行。

```bash
/home/yzj/miniconda3/envs/iaaa/bin/python -u scripts/benchmark_autonomous_concurrency.py \
  --source /path/to/frozen-experiment \
  --output-dir /path/to/new-benchmark-output \
  --levels 4 8 12 16 4
```

默认模型地址为 `http://127.0.0.1:8000/v1`，单请求超时 180 秒，等待原评估收尾的上限为 1800 秒。并发上限 16 对应当前服务器的 `max-num-seqs=16`；脚本不修改模型服务启动参数。

## 请求与校验

每城按固定路径哈希选择 3 个意图请求、15 个决策请求、6 个最终排名请求，共 48 个不同请求。各并发档位使用完全相同的消息、生成参数和结构化输出 Schema；不缩短回答、不减少轮次、不重试失败响应。

每条响应保留原始模型输出、usage、完成原因与请求延迟。校验使用现有运行时逻辑，包括重复 JSON 键、工作候选集合、停止/继续条件、固定工具顺序、最终 Top-10 唯一性，以及证据引用必须属于同一个 POI。原始已接受响应也先用这些校验器重放一次。

测速采用连续补充请求的队列。正式评估仍然按固定会话批次执行，因此这里的请求吞吐加速比不能直接当作完整 Agent 的端到端加速比。

输出包括：

- `manifest.json`：源协议身份、脚本哈希、完整请求样本与选样规则。
- `responses/`：每个档位每个请求的原始响应、usage、延迟与校验状态。
- `round_*.json`、`summary.json`：请求吞吐、输出 token 吞吐、P95/最大延迟、接口错误和内容校验错误。
- `progress.json`：当前档位与完成数。

## 如何解释

末尾再测一次 4 并发，用于暴露缓存预热与运行顺序影响。比较时使用较快的 4 并发结果，避免将预热收益全部归因于并发。模型服务的缓存不重置；这是当前服务状态下的吞吐测试。

若上一档出现接口错误或 P95 延迟超过请求超时的 80%，不继续向更高并发升级。内容校验错误单独保留，不因接口成功就视为正确。

2026-09-21 的部署选型还要求：相对较快的 4 并发，请求吞吐至少提高 20%、token 吞吐至少提高 15%；无接口或内容校验错误；P95 不超过 144 秒、最大延迟不超过 162 秒；输出 token 总数差异不超过 15%。吞吐相差 5% 以内时优先选较低并发。候选配置还需通过 24 个不同排名请求集中到达的压力测试，采用同样的正确性与延迟门槛。

这些是性能与稳定性门槛，不是推荐准确率调参。测速期间若 GPU 上有其他工作，结果只能代表共享负载下的实测表现。

## 切换正式配置

当前协议将并发写入身份哈希。提高正式并发必须使用新的冻结目录，并核对新旧协议唯一差异为 `execution.concurrency`。不原位修改运行中的代码或启动脚本，不将旧协议预测复制为新协议结果。

新配置仍按两城开发检查、两城独立验证、NYC 50/全量、TKY 50/全量顺序执行；旧全量 A 基线及已验证的 TKY 单例修复保持原来的核验复用方式。实际剩余耗时需要用新配置完整会话的进度继续校准。
